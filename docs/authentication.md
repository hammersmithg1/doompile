# Аккаунты, OAuth и файлы

Doompile использует персональные аккаунты во всех клиентах. Веб получает случайную HttpOnly-сессию, iOS/macOS и Web Clipper — персональный токен устройства после подтверждения в браузере. Общий `DOOMPILE_API_TOKEN` больше не принимается, в том числе в development. Публичная страница показывает лендинг, доступ к заметкам требует входа.

## Яндекс и Google

В Яндекс OAuth нужен тип **для авторизации пользователей**, платформа **Веб-сервисы**. iOS/Android LoginSDK для этого способа входа не нужен. Разрешения: `login:email` и `login:info`; Suggest Hostname можно не указывать, виджет не используется.

| Провайдер | Redirect URI для локального запуска | Redirect URI на сервере |
| --- | --- | --- |
| Яндекс | `http://localhost:3000/api/auth/yandex/callback` | `https://<домен>/api/auth/yandex/callback` |
| Google, Web application | `http://localhost:3000/api/auth/google/callback` | `https://<домен>/api/auth/google/callback` |

Redirect URI должен точно совпадать с адресом в кабинете провайдера. `DOOMPILE_PUBLIC_URL` задаёт внешний origin, включая порт локального сервера. За reverse proxy в production нужен HTTPS origin; заголовки `X-Forwarded-*` не используются как источник доверенного origin.

Передавай секреты через окружение сервера или менеджер секретов. Для нового сервера см. [быстрый старт](get-started.md#свой-сервер). Храни значения на стороне сервера, отдельно от исходников и клиентских настроек.

| ENV | Назначение |
| --- | --- |
| `DOOMPILE_YANDEX_CLIENT_ID`, `DOOMPILE_YANDEX_CLIENT_SECRET` | Яндекс OAuth |
| `DOOMPILE_GOOGLE_CLIENT_ID`, `DOOMPILE_GOOGLE_CLIENT_SECRET` | Google OAuth |
| `DOOMPILE_PUBLIC_URL` | Внешний origin; локально `http://localhost:3000` |
| `DOOMPILE_ADMIN_EMAIL` | Email администратора, без значения админка закрыта |
| `DOOMPILE_ADMIN_USER_ID` | Дополнительная привязка админки к одному UUID аккаунта |

Без пары ID/secret соответствующая кнопка неактивна. Google запрашивает `openid email profile`; сервер проверяет подпись ID token по JWKS, issuer, audience, срок действия и nonce. Яндекс проверяется через серверный обмен кода и `/info`, включая `client_id` и основной email. Оба провайдера используют одноразовый state, cookie привязки браузера и PKCE S256. Токены провайдеров не сохраняются и не отправляются клиентам.

Идентификатор аккаунта — неизменяемая пара `(provider, subject)`. Совпадающие email не объединяют аккаунты автоматически. Для одной коллекции на всех устройствах выбирай один и тот же способ входа. Изменение email у провайдера сохраняет аккаунт и заметки.

## Хранилище файлов

Профиль [для своего сервера](get-started.md#свой-сервер) поднимает MinIO через Docker Compose. Порт S3 привязан к loopback, а контейнер приложения подключается по внутреннему адресу `http://s3:9000`. Данные S3 сохраняются в отдельном bind mount, консоль выключена. [Исходники MinIO](https://github.com/minio/minio/releases/tag/RELEASE.2025-10-15T17-29-55Z)

| ENV | Назначение |
| --- | --- |
| `DOOMPILE_S3_ACCESS_KEY`, `DOOMPILE_S3_SECRET_KEY` | Серверные ключи S3 |
| `DOOMPILE_S3_ENDPOINT` | S3 API endpoint, только серверное окружение |
| `DOOMPILE_S3_REGION` | По умолчанию `us-east-1` |
| `DOOMPILE_S3_BUCKET_PREFIX` | По умолчанию `doompile`, затем `-<uuid пользователя>` |
| `DOOMPILE_S3_DATA_PATH` | Каталог данных MinIO на сервере |
| `DOOMPILE_S3_PORT` | Порт S3 на loopback, по умолчанию `9102` в Compose |

Приватный бакет создаётся при первом файле пользователя. Незагружавший файлы аккаунт занимает 0 байт. Клиенты не получают S3-ключей или публичных URL: скачивание идёт через авторизованный `/api/attachments/:id`, с поддержкой Range. Админка суммирует фактические размеры объектов S3; при недоступности хранилища показывает «Недоступно». Бинарные объекты адресуются SHA-256, повтор файла в одном аккаунте не увеличивает место. Удалённые заметки остаются tombstones; вложения автоматически не очищаются.

Для изолированных тестов без Docker можно явно задать `DOOMPILE_STORAGE=filesystem`. Этот режим работает только вне production и тоже разделяет файлы по пользователям. Локальный тестовый вход включается только сочетанием `NODE_ENV=development` и `DOOMPILE_DEV_LOGIN=1`; это отдельный аккаунт без прав администратора, автоматического обхода входа нет.

## Клиенты и агент

В iOS/macOS укажи адрес сервера и нажми **Войти через браузер**. В Web Clipper — **Войти через Яндекс / Google** либо **Взять подключение из приложения**. В браузере войди и явно разреши подключение. Затем вернись в приложение или снова открой popup расширения.

Подключение действует 10 минут и содержит отдельный случайный polling-secret, который не попадает в URL. После подтверждения секрет обменивается ровно один раз на токен устройства. Одного публичного кода или чужого Bearer-токена недостаточно, чтобы одобрить подключение. Веб-сессия действует 30 дней, токен устройства — 365 дней. Выход отзывает текущую сессию/токен на сервере. iOS хранит токен в Keychain, macOS — в приватном каталоге приложения, а браузерный клиппер — в хранилище расширения.

Агент может использовать тот же протокол:

1. `POST /api/auth/device`, JSON `{"label":"Название агента"}` → `code`, `secret`, `verificationUrl`.
2. Пользователь открывает `verificationUrl` в браузере, входит и подтверждает подключение.
3. `POST /api/auth/device`, JSON с `code` и `secret`, не чаще раза в 3 секунды → `pending` либо `approved` с персональным `token` и `user`.
4. API-запросы: `Authorization: Bearer <персональный token>`. Сохранять агентный токен следует в своём разрешённом скоупе setec.

Токен устройства не даёт доступ к админке даже владельцу. Для неё нужна веб-сессия с подтверждённым email из `DOOMPILE_ADMIN_EMAIL`; при заданном `DOOMPILE_ADMIN_USER_ID` должен совпадать и UUID. Адрес — `/admin`, ссылка появляется в настройках владельца. Админка показывает только список аккаунтов, время входа/активности и место в S3. Обычные пользователи получают 403 от её API.

## Разделение локальных данных и старые коллекции

На сервере идентичности и хеши сессий находятся в `identity.sqlite`, заметки и метаданные вложений — в `users/<uuid>/doompile.sqlite`. Веб использует отдельные IndexedDB, черновики, записи, каналы вкладок и блокировки синхронизации для каждого UUID. В запросах веба передаётся ожидаемый `X-Doompile-User-ID`: если cookie в другой вкладке переключилась на иной аккаунт, сервер возвращает 401 до чтения или записи данных. Service Worker не кеширует API, админку и страницы подтверждения подключения.

iOS/macOS разделяют SQLite, файлы, черновики, записи и токены по аккаунту и адресу сервера. Выход сохраняет персональные неотправленные данные на устройстве; повторный вход тем же способом в тот же аккаунт продолжает эту очередь, в том числе после истечения токена. Смена аккаунта создаёт новый контекст экрана. В клиппере каждая запись очереди навсегда привязана к исходному аккаунту и endpoint; другой аккаунт не видит и не отправляет эту очередь.

Старая общая серверная коллекция `data/doompile.sqlite` и `data/attachments` сохранена отдельно. Она **не назначается первому зарегистрировавшемуся пользователю**. После регистрации владельца выполнить явно, с остановленной синхронизацией его клиентов:

```sh
DOOMPILE_DATA_DIR="$PWD/data" DOOMPILE_S3_ENDPOINT=http://127.0.0.1:9000 \
TSX_TSCONFIG_PATH=apps/web/tsconfig.json \
  python3 ~/.agents/common/scripts/agent_secrets.py -- \
  node --import tsx infra/migrate-legacy.ts --user <UUID зарегистрированного владельца>
```

Перенос сохраняет ID, содержимое и метаданные, загружает старые файлы в бакет владельца; исходники остаются на месте. Ревизии новой коллекции начинаются с 1. Повтор с тем же неизменённым источником безопасен. Отличающиеся заметки с тем же ID в назначенной коллекции останавливают перенос.

Старые неподписанные локальные IndexedDB/App Group stores и unowned-очереди клиппера также остаются отдельно. Они не импортируются автоматически: нужно сначала определить владельца и перенести/экспортировать эти данные отдельно. Клипы, сохранённые до входа, не присваиваются следующему аккаунту.

## Проверки

```sh
npm run typecheck
npm test
npm run test:mobile
```

Реальный S3, multipart 33 MiB, Range, приватность бакетов, backup и restore проверяются отдельно на временных бакетах, которые тест удаляет:

```sh
DOOMPILE_S3_ENDPOINT=http://127.0.0.1:9000 DOOMPILE_S3_INTEGRATION=1 \
TSX_TSCONFIG_PATH=apps/web/tsconfig.json \
  python3 ~/.agents/common/scripts/agent_secrets.py -- \
  node --import tsx --test apps/web/lib/server/s3.integration.test.ts
```
